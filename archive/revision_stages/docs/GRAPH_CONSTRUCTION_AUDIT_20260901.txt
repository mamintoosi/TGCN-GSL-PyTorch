1. Executive Summary

This audit traces the complete path from DAGMA output to GCN/T-GCN message passing, verified line-by-line from source code. The key findings are:

1. The cached `W_est_*.npy` files store pre-thresholded weight matrices — the `w_threshold=0.3` is applied INSIDE `DagmaLinear.fit()`, NOT in the graph construction code. The stored file already contains mostly zeros with only ~8 nonzero entries per PH.

2. The graph is always binary — the GCN/T-GCN receives a binary (0/1) adjacency matrix, never weighted DAGMA coefficients. The actual weight magnitudes (0.31–0.62) are discarded.

3. The Laplacian normalization introduces a transpose — the code computes `D^{-1/2} (A+I)^T D^{-1/2}` instead of the standard `D^{-1/2} (A+I) D^{-1/2}`. For asymmetric graphs, this reverses the direction of message passing.

4. Node 128 is the dominant hub with out-degree 5 and in-degree 1. In the GCN, it aggregates from only 2 nodes (node 32 + itself), while its 5 outgoing edges are used by nodes 0, 50, 66, 102, 148.

5. The GSL graph has almost zero overlap with the physical graph — only 1 of 8 GSL edges exists in the physical graph. Jaccard = 0.002.

6. 147 of 156 nodes are completely isolated in the GSL graph. Only 9 nodes participate.

3. Edge Direction

DAGMA convention

For `W[i,j] > 0`: DAGMA interprets this as i → j (i influences j).

What the code produces (use_gsl=1)

The 8 directed edges in `adj`:

 |  Edge  |  W value  |  Interpretation  | 
 | --- | --- | --- | 
 |  32 → 128  |  0.617  |  Node 32 influences node 128  | 
 |  128 → 0  |  0.361  |  Node 128 influences node 0  | 
 |  128 → 50  |  0.314  |  Node 128 influences node 50  | 
 |  128 → 66  |  0.311  |  Node 128 influences node 66  | 
 |  128 → 102  |  0.481  |  Node 128 influences node 102  | 
 |  128 → 148  |  0.428  |  Node 128 influences node 148  | 
 |  102 → 150  |  0.372  |  Node 102 influences node 150  | 
 |  102 → 152  |  0.442  |  Node 102 influences node 152  | 

How the Laplacian normalizes direction

File: `utils/graph_conv.py`, function `calculate_laplacian_with_self_loop`:

```python
normalized_laplacian = matrix.matmul(d_mat_inv_sqrt).transpose(0, 1).matmul(d_mat_inv_sqrt)
```

Mathematically: L = D^{-1/2} (A+I)^T D^{-1/2}

The `.transpose(0,1)` transposes the intermediate result. For a symmetric matrix, this is a no-op. For asymmetric GSL graphs, it reverses the direction.

Concrete message-passing direction

In the GCN forward pass:
```python
ax = self.laplacian @ inputs  # L × X
```

For node j, the aggregated value is:
```
ax[j] = sum_i L[i,j] × inputs[i]
```

Since L = D^{-1/2} (A+I)^T D^{-1/2}, we have `L[i,j] ∝ (A+I)[j,i]`.

So node j aggregates from node i when adj[j,i] = 1 (edge j→i in the original graph).

This means: node j aggregates from its PREDECESSORS (nodes that have an edge TO j).

Verification with node 128

- Original edges: 32→128, 128→0, 128→50, 128→66, 128→102, 128→148
- adj[:,128] > 0 → node 32 (only one predecessor)
- After self-loop: node 128 aggregates from {32, 128} (2 nodes)

This is semantically correct for traffic prediction: node 128 learns from node 32 (its predecessor), which is the intended interpretation ("j at time t predicts i at time t+1").

⚠️ Normalization formula discrepancy

 |   |  Formula  |  Result  | 
 | --- | --- | --- | 
 |  Code  |  `D^{-1/2} (A+I)^T D^{-1/2}`  |  Node j aggregates from predecessors  | 
 |  Paper Eq. 2  |  `D̃^{-1/2} Ã D̃^{-1/2}`  |  Node j aggregates from successors  | 

The code's transpose actually corrects the direction for directed graphs: without the transpose, a directed edge i→j would mean j aggregates from successors (wrong for prediction). With the transpose, j aggregates from predecessors (correct).

For symmetric graphs (physical, cGSL), the transpose has no effect.

4. Thresholding

Where is `w_threshold` applied?

Inside `DagmaLinear.fit()` — the DAGMA library internally applies:

```python
W[np.abs(W) < w_threshold] = 0
```

before returning W. The default `w_threshold=0.3` is applied during the DAGMA optimization itself (in the `_adj` step of the loss function), not in the graph construction code.

What the graph construction code does:

```python
W_est = np.any(W_est_all > 0, axis=2)  # Boolean: True where ANY PH slice has W > 0
```

This is a positive-only threshold at value 0 (i.e., `W > 0`), applied AFTER DAGMA has already internally zeroed out ` | W |  < 0.3`.

Key insight: The code never applies its own thresholding. The `w_threshold=0.3` is entirely controlled by DAGMA's internal mechanism. The stored `W_est_*.npy` files already contain the thresholded values (most entries are exactly 0.0).

5. Binary vs Weighted Graph

The GCN/T-GCN always receives a BINARY adjacency matrix.

Evidence:
```python
adj = np.zeros(W_est.shape, dtype=int)  # dtype=int
adj[W_est > 0] = 1                       # Only 0s and 1s
```

The DAGMA weight magnitudes (0.31–0.62) are completely discarded. The GCN does NOT use:
- The weight values themselves
- Any weight-based normalization
- Any attention mechanism over weights

The only information preserved is edge existence (binary: 0 or 1).

6. Graph Normalization

File: `utils/graph_conv.py`

```python
def calculate_laplacian_with_self_loop(matrix):
    matrix = matrix + torch.eye(matrix.size(0))         # Step 1: Add self-loops
    row_sum = matrix.sum(1)                              # Step 2: Row sums
    d_inv_sqrt = torch.pow(row_sum, -0.5).flatten()     # Step 3: D^{-1/2}
    d_inv_sqrt[torch.isinf(d_inv_sqrt)] = 0.0
    d_mat_inv_sqrt = torch.diag(d_inv_sqrt)              # Step 4: Diagonal matrix
    normalized_laplacian = matrix.matmul(d_mat_inv_sqrt) \
        .transpose(0, 1).matmul(d_mat_inv_sqrt)         # Step 5: Normalize
    return normalized_laplacian
```

Mathematical formula: `L = D^{-1/2} (A+I)^T D^{-1/2}`

Where:
- `A` = binary adjacency matrix (156×156)
- `I` = identity matrix (self-loops)
- `D` = diagonal matrix of row sums of `(A+I)^T`
- `D^{-1/2}` = element-wise inverse square root of diagonal

Properties of the resulting L:
- Shape: (156, 156)
- Non-self-normalized: rows do NOT sum to 1
- Max eigenvalue: 1.0 (for connected components)
- For asymmetric GSL graphs: L is NOT symmetric

Self-loop handling

Self-loops are ALWAYS added, regardless of whether the input has them. This means:
- Physical graph (no self-loops): gets self-loops added
- GSL graph (no self-loops): gets self-loops added
- All nodes always include their own features in aggregation

What is NOT normalized

- The raw DAGMA W is NOT normalized
- No softmax, min-max, or z-score normalization is applied to W
- No row normalization or column normalization of the adjacency
- No degree-based edge weighting

7. PH Handling

Each prediction horizon (PH=1,2,3,4) runs as a separate experiment with its own config file:

```
configs/gcn-sz-gsl-pre_len1.yaml  →  use_gsl=1, pre_len=1
configs/gcn-sz-gsl-pre_len2.yaml  →  use_gsl=1, pre_len=2
configs/gcn-sz-gsl-pre_len3.yaml  →  use_gsl=1, pre_len=3
configs/gcn-sz-gsl-pre_len4.yaml  →  use_gsl=1, pre_len=4
```

Each run:
1. Creates a new `SpatioTemporalCSVData` with the specified `pre_len`
2. Calls `compute_adjacency_matrix()` which loads/creates `W_est_shenzhen_pre_len{PH}.npy`
3. Each PH has its own cached W_est file
4. The resulting adjacency is passed to a fresh GCN/T-GCN model

DAGMA input per PH:
```python
X = data[i::self.pre_len]  # Subsampled: takes every pre_len-th row starting from i
```

For PH=1: `X = data[0::1]` (all rows)
For PH=2: `X = data[0::2]` (every 2nd row), `X = data[1::2]` (offset by 1)
For PH=3: `X = data[0::3]`, `data[1::3]`, `data[2::3]`

However, after `np.any(W_est_all > 0, axis=2)`, the resulting graph is the same 8 edges for all PH values. This means:
- DAGMA learns slightly different weights per PH subsample
- But the same edges survive the threshold across all PHs
- The GCN/T-GCN effectively uses the same graph for all prediction horizons

11. Potential Implementation Issues

Issue 1: Binary graph discards weight information

Fact (verified from code): The adjacency is `dtype=int` with values 0 or 1. DAGMA weight magnitudes (0.31–0.62) are discarded.

Impact: The GCN cannot distinguish strong edges (W=0.62) from weak edges (W=0.31). All edges have equal influence in message passing. This is a fundamental limitation of the current implementation.

Severity: Moderate. This is a design choice, not a bug. However, weighted graphs could potentially improve performance.

Issue 2: Normalization uses (A+I)^T instead of (A+I)

Fact (verified from code): The code computes `D^{-1/2} (A+I)^T D^{-1/2}`.

Impact: For asymmetric graphs (GSL, physical), this reverses the direction of message passing. For the GSL graph, this actually produces the CORRECT direction (node j aggregates from predecessors). For the physical graph, which is also asymmetric, this also reverses direction.

Severity: This is likely intentional but should be documented. The physical graph's direction convention may differ from the GSL graph's convention.

Issue 3: np.any() across PH slices collapses all PH-specific graphs

Fact (verified from code): `W_est = np.any(W_est_all > 0, axis=2)` takes the union of edges across all PH subsamples.

Impact: If DAGMA learns different edges for different PH subsamples, the union may include edges that are only relevant for certain PHs. In practice, the same 8 edges appear for all PHs, so this is not currently a problem.

Severity: Low (not currently causing issues, but the design is fragile).

Issue 4: 147/156 nodes are isolated

Fact (computed from cached files): Only 9 nodes participate in the GSL graph. The remaining 147 nodes rely entirely on self-loops in the GCN.

Impact: For 94% of nodes, the GCN's graph convolution is equivalent to just using self-loops (i.e., no graph mixing at all). The graph structure learning only helps 9 out of 156 nodes.

Severity: High. This is the core scientific concern: the learned graph is so sparse that it provides almost no structural information for most nodes.

Issue 5: Physical graph is also asymmetric and not symmetric-normalized

Fact (verified from data): `np.allclose(adj_phys, adj_phys.T)` is False. The physical graph has 532 directed edges and is not symmetric.

Impact: The same normalization issue (Issue 2) applies to the physical baseline. Both graphs undergo the same D^{-1/2} (A+I)^T D^{-1/2} normalization, so the comparison is fair.

Severity: Low (fair comparison, but the normalization convention should be documented).

12. Conclusions

What the code does

1. DAGMA learns a weight matrix W with `w_threshold=0.3` applied internally
2. The cached W_est file stores the thresholded W (mostly zeros)
3. The code converts W > 0 to a binary adjacency matrix
4. Self-loops are added
5. The graph is normalized via D^{-1/2} (A+I)^T D^{-1/2}
6. The GCN/T-GCN performs graph convolution using this normalized Laplacian
7. The convolution aggregates features from predecessors (due to the transpose)

What the GCN actually sees

For the GSL graph (use_gsl=1, PH=1):
- 8 directed edges connecting 9 nodes
- 147 isolated nodes with only self-loops
- Binary weights (no magnitude information)
- Normalized Laplacian that is NOT symmetric

Scientific implications

1. The graph is extremely sparse — 8 edges for 156 nodes is 0.03% density
2. Almost no information flows through the graph for 94% of nodes
3. The weight magnitudes are discarded — all edges treated equally
4. The graph is identical across PH=1..4 — no horizon-specific adaptation
5. Only 1/8 GSL edges overlap with the physical graph — almost no shared structure
